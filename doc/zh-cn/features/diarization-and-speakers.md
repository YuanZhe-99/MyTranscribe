# 谁在说话

*由里程碑 M5 交付。*

有些模型在返回文字时会附上说话人标签。有这项能力时，转写稿会写明谁在说话，用户可以给他们命名。

## 是否提供该功能

依据模型自身的能力字段：

- **支持** —— 提供，且默认开启。
- **未知** —— 提供，默认关闭，并注明该模型尚未验证。若服务器拒绝该请求，应用会提供"不带它再试一次"，而不是
  让用户自己去找那个设置。
- **不支持** —— 不提供，并说明该模型做不到，若这一判断有误可以在库中修改该字段。

要求识别说话人会改变请求的构造方式，有时也会改变窗口的最大长度。规划器会把两者都算进去。

## 难点：一个人，多个窗口

长录音会被切成多个窗口，每个窗口独立标注。在第一个窗口里把某人叫作"说话人 1"的模型，并不知道它在第二个窗口
里叫作"说话人 2"的是同一个人。放着不管，两个人聊一小时会返回来十几位说话人。

有两件事解决它，还有第三件收拾它们漏掉的部分。

**重叠窗口投票。** 相邻窗口有意共享一段音频 —— 要求识别说话人时这段更长，因为这正是那段重叠的用途。两个窗口
都转写了那一段，因此都为同一段话打了标签。把两者对齐就得到直接证据：本窗口的标签 B 就是上一个窗口的标签 A，
因为它们覆盖同样的秒数、说的是同样的话。证据薄弱或含混时，该标签会成为一位新的说话人，而不是一个错误的猜
测 —— 多出一位陌生人由用户合并只是小麻烦，两个人被悄悄并成一个则是一份坏掉的转写稿。

**声音样本往下传。** 在 API 接受已知说话人参考时，应用会从每位说话人首次被识别的位置截一小段样本，随下一个
窗口一起发送。模型于是会用同一个名字返回该说话人，无需任何推断。这是可靠的路径，有些服务提供，有些不提供。

**由用户决定。** 说话人面板可以合并两位说话人、把某位归为未知，也可以给任何人起名；句子编辑器可以把某一句
移给别人。每个操作都只改动一条记录，而不是重写文字；由于原始回复被保留，匹配可以重跑而无需再次上传任何
东西。

"未知"是合并的另一半，它存在是因为匹配会朝两个方向出错。一个人被拆成两位，用合并来修。而某个标签根本就不
是一个人 —— 一段交叉说话，或者证据不足时的一次猜测 —— 修法是承认没人知道，这比把它并进一位**确实存在**的
说话人要诚实。这些句子随后会在界面和所有导出里显示为"未知"，面板也会用单独一行统计它们。这一切都不会自动
发生；一台机器自作主张认定自己没把握，正是转写稿丢掉已经正确识别的说话人的方式。

**用过的名称。** 给说话人起过的名字会被记住，下一次的重命名对话框会把它作为一个轻点即可套用的标签提供出
来。同样那几个人会在一段又一段录音里出现，每次都重新输入正是让功能被弃用的那种摩擦。该列表与其余配置一起同
步，因为你录音里的人在两台设备上是同一批人；可以在设置 › 转写 › 说话人名称里整理，也可以在对话框里删掉某个
标签。

## 它做不到什么

在不提供声音样本的服务上，一个人若在整段重叠期间一言不发，就会作为第二位说话人返回。没有任何证据把他们连起
来，而凭空造一个只会更糟。面板会标出它最没有把握的那些边界，这样修正就是在应用已经起疑的地方点一下，而不是
在整份转写稿里翻找。
