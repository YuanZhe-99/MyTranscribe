# 版本历史

新的在前。每条记录说明改了什么，以及在重要之处说明为什么 —— 事后最难还原的正是理由。

## 0.3.5 — 2026-09-25

在设备上标注说话人（本地模型计划的 L8）。

- 设置 › 本地模型 › 说话人标签 会在说明大小和来源之后下载一个 35 MB 的包。有了它，本设备上的任务也能使用
  **说话人**，适用于任何本地模型：每个窗口转写完之后加上标签，再用与远程任务相同的说话人匹配，让同一个人在
  各个窗口中始终是同一位说话人。
- iPhone 和 iPad 上没有：应用在那里没有运行它的运行时。
- 它在这里用一段两人的简短片段检查过，没有在长会议上与服务的标签比较，所以和本设备上的其他路线一样标为未测试。

## 0.3.4 —— 2026-09-25

在 Apple 设备上，系统自带的语音识别可以作为回退（本地模型计划的 L6）。

- 在 iPhone、iPad 和 Mac 上，设置 › 本地模型 ›"所选处理器失败时"多了第三个选项：系统的语音识别。本设备上的
  模型无法运行时，任务改用它继续，并如实说明。
- 它只在设备上运行 —— 应用要求在设备上识别，所以音频不会发送给 Apple —— 应用在它第一次运行时才请求使用语音
  识别的权限，绝不会在你选择它之前请求。隐私政策也这样写明。
- Android 不支持：它的识别器需要把本项目不接受的代码编译进应用。

## 0.3.3 —— 2026-09-25

Parakeet 可以在 Apple 神经网络引擎上运行了（本地模型计划的 L4）。

- 在 iPhone、iPad 和 Mac 上，Parakeet 现在可以通过 FluidAudio 在神经网络引擎上运行，使用它自己的 Core ML
  模型包（483 MB）。应用像下载其他模型包一样下载它 —— 逐个文件，按公布的哈希核对 —— FluidAudio 自带的下载器
  保持关闭。
- **最低系统要求现在是 iOS 17 和 macOS 14（Sonoma）。** FluidAudio 需要它们。iPhone 8、8 Plus 和 X，以及
  2018 年之前的 Mac（2019 年之前的 iMac，2017 年的 iMac Pro 除外）停留在 0.3.2。
- 这条路线还没有在这里的 Apple 设备上运行过：它在 GitHub 的 macOS 机器上构建，标明未经测试；和每条路线一样，
  它会先在设备上做十秒检查。

## 0.3.2 —— 2026-09-25

本地模型可以用 GPU 了，前提是设备自己的驱动能接住它（本地模型计划的 L3）。

- Whisper 和 Parakeet 现在会为设备上的每个 GPU 提供一条路线：Windows x64 电脑和 Android 9 及以上手机上的
  Vulkan，Windows on ARM 与 Android 上高通 Adreno GPU 的 OpenCL，以及和以前一样的 Apple 设备上的 Metal。只有
  设备自己的驱动能加载时，GPU 路线才会出现；并且只有在它于该设备上通过十秒检查后才会运行。
- 这些路线都没有在这里的真实硬件上测试过 —— 开发机的骁龙 8cx Gen 3 没有 GPU 后端能用的驱动 —— 所以每一条都
  标明未经测试。在 Windows x64 电脑上，Vulkan GPU 通过检查并且比 CPU 快时，自动选择会用它；Adreno 和 Android
  上的路线只在你选择时运行。
- GPU 后端让应用变大了：Windows x64 上多约 55 MB，Android 上多约 45 MB。

## 0.3.1 —— 2026-09-25

设备上又多了两个模型系列：Parakeet TDT 0.6B v3 和 Qwen3-ASR 0.6B（本地模型计划的 L2）。

**Parakeet，用的是已经在那里的库**

- Parakeet 运行在 whisper.cpp 自带的 Parakeet 运行时上，它和 Whisper 在同一套预编译库里，所以不给应用增加
  第二个运行时 —— 只在你下载时多一个 638 MiB 的模型。在开发机上，它在 CPU 上的检查用时是实时的三分之一，而
  Whisper turbo 用了实时的两倍半。它能写 25 种欧洲语言，不能写中文、日语和韩语，这些语言的任务也绝不会交给它。
- 它的窗口长两分钟：运行时一次读完整个窗口，较短的窗口能让手机的内存保持可控。句子依据它给每个词的时间来切分。

**Qwen3-ASR，覆盖 Parakeet 顾不到的一切**

- Qwen3-ASR 运行在 sherpa-onnx 上，用的是 sherpa-onnx 自己的预编译库，像 whisper.cpp 的一样按哈希固定。它把任务
  的关键词当作优先识别的词。它不给时间戳，所以每个 30 秒的窗口成为覆盖整个窗口的一行，标明没有真实时间。
- 暂不支持 iOS：sherpa-onnx 没有为它发布库，模型会说明它在那里无法运行。
- 被取消的 Qwen 窗口会先跑完，任务才停下：sherpa-onnx 无法中途停止一个窗口。

**另外**

- 在桌面上，本地模型现在会留出两个处理器核心：在开发机上，用满所有核心会让模型慢 60%。

## 0.3.0 —— 2026-09-25

第一个不借助转写服务也能转写的版本：Whisper large-v3 和 large-v3-turbo 通过 whisper.cpp 直接在设备上运行，
覆盖应用发布的每个平台。它是本地模型计划的前两个里程碑（L0 和 L1；见 [`decisions.md`](decisions.md)）。

**本设备**

- 模型库 › 本设备列出应用能在本地运行的模型。只有在你点击时才下载，中断后从断点继续，逐个文件按公布的哈希
  核对，并一步安装，因此下载到一半的模型绝不会显示为已安装。模型只留在设备上：从不同步、备份或导出，在
  Android 上也不进入自动备份。
- 安装之后，应用会在第一个任务之前用一段十秒的公有领域片段在本设备上检查这个模型，并记录它运行得多快。检查
  失败、或在运行中让应用崩溃过的路线不会再被自动使用；任务会按设置中的回退策略继续，默认是在 CPU 上用同一个
  模型。
- 新建任务时可以选择"本设备"作为来源。它像其他任务一样被切分成窗口，音频不离开设备，任务页会说明每个窗口
  实际在哪里运行。
- 设置 › 本地模型 › 诊断 显示引擎找到了什么 —— 它的版本、CPU 特性、设备 —— 并能复制一份不含文件名和文本的
  报告。

**如实说明测试过什么**

- 这个应用运行的大多数设备，本项目都没法测试。在这样的设备上，模型会标明未经测试；自动选择只按
  `engine-routing.md` 中的规则在那里使用加速器，CPU 始终是底线。
- 在骁龙开发机上，全精度的 turbo 在 CPU 上转写一段 81 分钟的讲座，用了实时的 1.8 倍 —— 比实时慢。对可以等的
  录音它是可用的；让它变快的，是量化模型包和接下来几个里程碑的 GPU 路线。

**它是怎样构建的**

- whisper.cpp 以预编译库的形式到来，按哈希固定：Windows x64 和 Apple 平台用上游自己的，Windows ARM64 和
  Android 用本项目对同一版本的构建。应用构建不编译任何原生代码，这让每个平台的构建都保持在几分钟之内。
- 隐私政策新增"下载"一节：应用只在你要求下载时才连接模型托管方。

## 0.2.1 —— 2026-09-09

第一段真正被留下来的录音找出来的问题。一场三位说话人、三百多行的 Microsoft 会议，读过、改过、放了一晚上。
由此得到六件事。

**留不住的重命名**

- 改完说话人名字，返回再打开转写稿，又变回了"Speaker 1"。写入一直是对的；持有转写稿的 provider 从未刷新，
  所以第一次之后的每一次打开，拿到的都是第一次读出来的那份，直到应用重启为止。现在有了修订计数器 —— 与任务
  列表早就在用的形态相同 —— 阅读器也会保留上一次读到的副本，这样刷新不会把页面换成加载圈、丢掉滚动位置。从
  同步到达的更新副本会替换页面手上的那一份。
- 顺带修了两个相邻缺陷。窄窗口下说话人面板以底部面板呈现，它只构建一次、并且比打开它的那次构建活得更久，所以
  同一次面板会话里的第二次改名是基于第一次之前的转写稿做出的，把第一次覆盖掉了。另外，重命名对话框在被关闭的
  那一刻就释放了输入框，而此时关闭动画还没结束 —— 下一帧就会抛异常。

**应用不问自答写出的文件**

- 转写完成后，过去会在录音当时所在的任意文件夹里留下一个 Markdown 和一个文本文件。那里不是应用可以擅自写入
  的地方，用户也未必还留着那个文件夹。现在它是设置 › 转写里的一个开关，**默认关闭**。无论开关如何，转写稿本
  身都保存在应用自己的文件夹里。
- 详情页不再列出那些路径。它显示的文件位置可能早就被搬走或清空了。

**给人起名**

- 之前给说话人起过的名字会被记住，并在重命名对话框里作为轻点即可套用的标签提供出来。同样那几个人会在一段又一
  段录音里出现，每次都重新输入正是让功能被弃用的那种摩擦。该列表与其余配置一起同步，因为你录音里的人在两台设
  备上是同一批人；设置 › 转写 › 说话人名称可以管理它。
- **未知。** 说话人匹配会朝两个方向出错，而过去只有一个方向有修复手段。一个人被拆成两位，用合并来修。某个标
  签根本就不是一个人 —— 一段交叉说话，或者证据不足时的一次猜测 —— 现在可以归为未知来修，这比把它并进一位确
  实存在的说话人要诚实。这些句子在界面和全部六种导出格式里都显示为"未知"；此前导出带说话人的 Markdown 会在
  它们上方印出一个空白的 `**Speaker**`。这一切都不会自动发生。

**转写会同步了**

- 每条已完成转写的文本现在会传到你自己的 WebDAV 服务器，也会进入每一个本地备份和 ZIP 导出，所以在一台设备
  上做的转写在另一台上也能读。任务文件夹仍然不是数据模块：每个文件夹里较小的那一半 —— 记录和转写稿，绝不包
  括音频 —— 会在同步前被投影进一个属于它自己的文件，同步后再写回，所以几个小时的私人音频依旧不可能被误放进
  备份包。
- 删除一条转写会在下次同步时传到你的其他设备。正在重跑的转写则不会：它在投影里会被冻结而不是丢弃，否则它的临
  时缺席会被读成删除，对端设备会在用户看着录音重新转写的同时，把整个文件夹连同音频一起删掉。强制下载、还原备
  份和导入 ZIP 都只增不删：它们都没有基线快照，无法区分"服务器从来没有过这条"和"有人删了这条"。
- 通过同步到达的转写在本设备上没有录音，所以它的页面不提供"重新运行"。

**音频，如果你需要的话**

- 转换后的回放副本也可以传输，开关在同步页的"同时同步音频"。它**默认关闭，按设备设置**：空间充裕的笔记本和
  快满了的手机需要不同的答案，而转写文本两种情况下都照常同步。开关关闭时，完全不会发出任何与音频有关的请求。
  原始录音永远不会传输。
- 设置 › 数据 › **移除转换后的音频**可以一次释放本机所有回放副本，并显示能释放多少空间。所有转写稿都会保
  留，照样可读、照样同步，下次同步也不会把音频拉回来。

**此外**

- 转写稿的写入现在与任务记录一样带重试，后者从 0.1.0 起就有了。原子替换本质上是一次重命名，而在 Windows 上
  只要有别的东西打开着该文件，重命名就会直接失败。

## 0.2.0 —— 2026-09-06

第一段真实录音找出来的问题。一场八十一分钟的讲座带说话人识别，八十秒内经 OpenRouter 端到端跑完。转写本身的
每一个环节都工作正常。这个版本修的全是应用拿到结果之后所做的事。

**那个没有察觉的页面**

- 一个在自己页面开着的时候完成的任务，会一直显示"等待中"和一个"开始"按钮，直到应用重启为止 —— 而旁边的列表
  写着"已完成"。执行器在任务停下时发布了一个空队列，页面便退回到它在任务还在等待时读到的那份记录；因为除了某
  个页面因按钮被按下而恰好刷新列表之外，从来没有东西会重新读取任务记录。现在执行器会保留刚刚结束的那个任务，
  并为自己写下的每一条记录计数；页面盯着这个计数，并在同时可能存在的三份副本中取最后写入的那一份。
- 那个"开始"按钮并非无害：按下它会从各分段重新生成转写稿，把查看器里做过的所有修正统统丢掉。已完成的任务现在
  提供的是**重新转写**，并会在执行前说明这样做要付出什么代价。

**转写稿本身**

- 八个接缝处各有十九秒的话被重复了。用来去掉重叠的切点，前提是分句相对重叠而言足够短；而以整段作答的模型返回
  的分句长达数分钟，于是切点两侧的分句各自都覆盖了整段共享内容。现在比较要看多远改为从重叠推算，不再固定为四
  十个词元；重复也改为按一条链来追踪，可以跨过同一段话的两份转写中零散不一致的词。八个接缝里有七个干净了；第
  八个一边写"two vectors"、另一边写"2 vectors"，几乎不共享任何完全相同的内容，那里什么都不删 —— 这正是合并
  一直以来的规则。
- 五个不同的人被印成了同一个人。写在录音旁边的那两个文件渲染的是各个窗口自己的说话人标签，于是每个窗口的
  `S1` 读起来都像同一个人。现在它们从统一后的转写稿渲染，用的就是查看器导出所用的那套格式化器。
- 说话人被编成了 1、2、3、5、6。那个编号取自 id，而匹配为它安置的每一个窗口标签都会分配一个 id —— 包括某个唯
  一的那句话后来落在被裁掉的重叠里的标签。现在显示的是说话人的位次。id 本身不动：它们是样本文件的名字，接受
  参考音频的服务也会把它们回传。

**设备上的空间**

- 详情页会说明一次转写占用了多少空间，并在转写稿已经存在之后，提供把录音的转换副本还回去的选项 —— 那场讲座是
  三十九兆，此前既看不到它，也没有办法在不删除整条转写记录的前提下删掉它。转写稿、原始回复和说话人样本都会
  保留。
- 没有转换副本时，播放会回退到原始录音。小到可以整段上传的录音从来就没有副本，而播放条此前会在文件就摆在那里
  的情况下说没有可播放的内容。
- 任务完成时被别的程序占用的分段音频会永久留下。现在删除会重试，仍未删掉的会在下次启动时被清扫。

**命名**

- 一次转写可以有自己的名字，在详情页修改，或长按它在列表中的那一行修改。它只是一个标签：录音旁边的文件保留录
  音的名字，导出则采用新名字。任务正在运行时也可以改名。

## 0.1.0 —— 2026-09-05

第一个发布版本：录音进去，转写稿出来；应用知道如何切分一份大到无法整段发送的录音、从被打断的地方继续、在各
片之间保持说话人的同一身份，并拒绝把 API Key 送往不该送的地方。

**转写**

- 来源与模型成为一个库，带上每个模型的真实上限，以及每项能力的三态答案，因此"没有人验证过这一点"可以直说，
  而不是靠猜。
- 一个规划器，在任何上传之前决定如何切分录音并说明理由。那些原始脚本要求用户传入一个分段长度，事后才告诉他
  们行不行。
- 一个任务引擎，在每个窗口之后记录状态，因此中途关闭应用最多损失正在传输中的那一个窗口，继续时会复用一切已经
  付过费的部分。
- FFmpeg 在 Android、iOS 与 macOS 上链接进应用；在 Windows 上使用外部可执行文件并附带下载助手，因为维护中的
  插件只发布 x86_64 的 Windows 二进制。

**阅读**

- 一个双模式查看器：连续段落用于阅读，逐行视图用于修正。搜索、字号、说话人名字与颜色，以及一条可从某一句跳
  转并跟随播放的音频条。
- 六种导出格式。只有模型返回了真实时间时才提供字幕 —— 差一分钟的 SRT 看起来像是能用，比没有还糟。

**说话人**

- 基于两个窗口共享的秒数做跨窗口匹配，并把声音样本传给接受它们的服务方。
- 阈值宁可拒绝一次可疑的匹配，也不去猜；把两位说话人合并成一位只需点一下。错误的合并会让转写稿把话安错人，且
  事后没有任何东西会揭示它；漏掉的合并只是列表里多出一位说话人。

**密钥**

- API Key 只在 HTTPS 下、或在明文 HTTP 到一个无法离开用户自己网络的地址时，才会送往 WebDAV 服务器 —— 私有地
  址段、Tailscale 或 ZeroTier 名称、mDNS 名称，或者他们在该设备上信任的主机。其余内容照常同步。
- 被拒绝的地址不会产生任何请求，两个方向都不会。

**外壳与约定**

- 三个标签页 —— 转写、库、设置 —— 建立在单个 `go_router` `ShellRoute` 之上，从 600 逻辑像素起使用导航栏、以
  下使用底部栏，两者由同一份目的地列表构建，因此不会各走各的。
- `FlexScheme.tealM3`，选它是为了一眼就能与四个兄弟应用区分开。
- 英语、简体中文与繁体中文的本地化，并有测试在词条互相偏离、译文改了占位符名称、或中文词条里仍留着英文时
  失败。
- 系列的自适应布局策略模块，核心逐条照搬，并扩展了本应用自己的分栏规则。它们的推导在 `adaptive-layout.md`。

**数据**

- 一个会同步的数据模块 `transcribe_settings.json`，把来源、模型与默认值作为一列带不透明载荷的扁平记录保
  存 —— 这样新版本写入的记录在这里也能正确合并，即便本版本无法解释它。
- `myapps_data` v1.0.2 之上的四个共享服务外观层，以及 WebDAV、备份、许可证与隐私页面。
- API Key 与任务目录有意**不是**数据模块，这正是它们在结构上（而非靠过滤）被排除在同步、备份与 ZIP 导出之外
  的原因。

**值得记住的决定**

- 设置合并判断两次编辑是否"相同"，依据的是记录的 id、kind 与 payload，**而不是**时间戳。两台设备相隔一分钟把
  同一个来源改成同样的名字，并没有产生任何分歧，否则共享引擎会在两份一模一样的配置之间报出冲突。
- Windows 使用外部 FFmpeg 可执行文件而不是插件自带的库，因为维护中的插件只发布 x86_64 的 Windows 二进制，而
  本项目是在 Windows on ARM64 上开发的。`platform-notes.md` 记录了整套安排。

**由测试而非用户发现的缺陷**

- 中途失败或被取消的任务，是从它**开始时**的那份记录写回的，抹掉了方案和所有已完成的窗口。下一次运行会把它们
  全部再付一遍钱 —— 而那正是续传存在要防止的唯一一件事。
- 原子写入是一次重命名，而在 Windows 上，只要有别的东西持有该文件，重命名就会直接失败 —— 正在读取它的任务列
  表、杀毒软件、搜索索引器。一次持续一毫秒的冲突就可能杀掉一个一小时的任务。现在读写都会重试。
- 加方括号的公网 IPv6 地址不含点，因此落到了"把无点主机视为本地"的规则上，本会被当作可以发送密钥的安全去处。
