# WebDAV 同步

同步在用户完成配置之前一直关闭，而且只与用户填写的服务器通信。它携带**配置**（来源、模型和默认值）、已完成转写的**文本**，以及在端点安全时携带 API 密钥。录音永远不会同步；转换后的回放副本只在明确要求的设备上传输。

引擎本身位于共享的 `myapps_data` 包中，文档在 `packages/myapps_data/doc/zh-cn/`。本页说明它在这里是如何配置的。

## 注册了哪些文件

两个数据模块，顺序如下：

| 文件 | 模块 id | 携带的内容 |
|---|---|---|
| `transcribe_settings.json` | `settings` | 来源、模型、本地模型和默认值 |
| `transcribe_transcripts.json` | `transcripts` | 每条已完成转写的记录和文本 |

远端目录是 `/MyTranscribe`。`lib/app/data_modules.dart` 是这些名字唯一出现的地方。再增加模块只能追加到注册表末尾，绝不能插到这两个之前——引擎把注册顺序视为有意义的。

任务文件夹仍然不是模块。各引擎只会碰上面这些文件名，这正是几个小时的音频不会进入备份包的原因。

本地模型只以记录的形式传输，别无其他。一条 `localModel` 记录 —— 名称、语言、能力、它的模型包 id —— 像来源一样同步，因此在一台设备上添加的模型会在另一台上显示为"未下载"。`models/` 中已下载的模型包和 `local_engine_state.json` 中的设备引擎状态都不是模块：数 GB 可以重新下载的文件，以及关于某一台设备处理器的事实，都不该出现在服务器上。

旧版本会把本地模型记录带过去，只留下一个本版本会修复的瑕疵：0.2.x 会把它不认识的记录 kind 写回成 `unknown`。每个本地模型 id 都以 `local:` 开头，一条 id 如此的 `kind: unknown` 记录在这里会被重新读作本地模型 —— 并在下次保存时以正确的 kind 写回。本版本自己则会把未知的 kind 按读到时的样子原封不动地写回，因此以后的版本新增的 kind 经过本版本走一个来回也能保留下来。

## 一次同步的过程

1. 从 `jobs/` 重新生成 `transcribe_transcripts.json`。
2. 获取远端 `.lock`，避免两台设备同时上传。
3. 对每个模块：下载远端文件。若不存在，就把本地文件作为新文件上传。若两边原始字符串完全相同，保存基线快照并结束——这是快速路径，也是文件格式必须与应用写出的格式一致的原因。
4. 否则做三方合并：本地、远端，以及上次达成一致时的基线快照。
5. 把合并结果写到本地、上传、保存新的基线快照、释放锁。
6. 把转写模块的合并结果写回 `jobs/`。
7. 在锁之外交换 API 密钥，然后交换音频。

`.sync_base/` 中的基线快照正是删除能够传播而不是"复活"的原因：出现在基线中、本地却没有的记录，说明是在本机删掉的，而不是在对端新增的。

## 合并规则

`lib/shared/services/sync_merge.dart` 封装了共享的 `mergeRecords` 引擎，两个模块都用它。记录以 id 为键，按 `modifiedAt` 比较。

- 只有一边改动 → 那一边胜出。
- 两边都没改 → 保持本地不变。
- 某一边新增的记录 → 保留。
- 一边删除、另一边未动 → 删除传播。
- 一边删除、另一边编辑 → 编辑胜出；有意的改动优先于"不存在"。
- 两边都改了 → **冲突**，除非内容相同。

"内容相同"比较的是记录**说了什么**，而不是何时说的：设置记录比较 `id`、`kind` 和 `payload`；转写记录比较 id、去掉 `modifiedAt` 的任务记录，以及转写稿。两台设备前后相差一分钟把同一个说话人改成同一个名字，并没有产生分歧，让用户在两份完全相同的转写稿之间选择只会是噪音。

冲突**绝不**自动解决，所有调用点的 `autoResolve` 都是 false。每条冲突记录都会弹出一个对话框，显示两个版本及各自的时间；只要取消其中任何一个，整个解决过程就中止：什么都不上传，冲突保持待处理，也不会悄悄保留某一方。用户回答过的冲突会在重新获取锁之后完成。对话框渲染的是 `SyncConflictView`，所以每个模块都自己决定如何描述自己的记录：设置记录列出 payload 字段，转写记录列出说话人和行数。

胜出的版本仍会吸收另一方的未知字段，所以在冲突中落败绝不会删掉新版本写入的字段。

## 转写记录

`transcribe_transcripts.json` 是 `jobs/` 的**投影**，而不是第二份真相。它在引擎运行前从任务文件夹重新生成，运行后再写回去，由 `TranscriptSyncService` 负责。每条记录携带一个 `job.json` 和一个 `transcript.json` 的原始内容，不做解析。

之所以保留原始内容，是因为任务记录内部的嵌套类型没有自己的 `extraJson`。解析新版本写出的记录再写回去，会丢掉那个版本新增的字段，两台设备就会轮流剥掉对方的字段并永远重新上传。

有三条规则保护这些文件夹，每一条都对应一种否则就会丢数据的情形：

- **只有已完成的转写才会被重新投影。** 未完成、但出现在上一份投影里的任务（正在重跑的那种）会原样保留下来。否则它的"消失"会被读成删除，对端设备会在用户看着录音重新转写的同时，把整个文件夹连同音频一起删掉。
- **删除只来自三方合并。** 写回时只删除那些出现在同步前投影里、同步后却不见了的 id。强制下载、还原备份和导入 ZIP 都只增不删：它们都没有基线快照，无法区分"服务器从来没有过这条"和"有人删了这条"。只有一台设备有的转写，下次会重新上传。
- **绝不投影出一个缺口。** `job.json` 存在却读不出来时，整个操作会在发送任何东西之前中止，磁盘上的旧文件保持原样。少写一条记录等于告诉对端设备用户删掉了它。

写回时还会跳过运行器正在占用的任务，绝不重建同步过程中被删掉的任务，并拒绝 id 可能指向 `jobs/` 之外路径的记录。

通过这种方式到达的转写在本设备上没有录音，所以它的详情页不会提供"重新运行"。

每次同步都会下载整份文档——引擎目前还没有 ETag 短路。一年的录音大约十兆字节，可以接受；条件式 GET 属于共享包的工作。

## 音频

转换后的 `jobs/<id>/audio.mp3`（应用为切分窗口而生成、播放器也在放的单声道 16 kHz 副本）通过应用层的旁路通道传输，放在数据文件旁边的 `audio/` 目录里。原始录音永远不会离开设备：它可能有好几个 GB，而且是用户自己决定放在哪里的。

这项功能**默认关闭，按设备设置**，开关在同步页的"同时同步音频"。空间充裕的笔记本和快满了的手机需要不同的答案，而转写文本两种情况下都照常同步。开关关闭时，完全不会发出任何与音频有关的请求。

交换在两个方向上都只增不改：本设备有而服务器没有的文件会上传，反之则下载。二进制文件是不可变的，所以不需要合并，也不需要锁。列目录失败不会被当成"服务器是空的"——那会因为一次不稳定的请求就把所有文件重传一遍。用"移除转换后的音频"删掉的音频会在任务文件夹里留下 `audio.discarded` 标记，不会被重新取回；重跑并生成新副本时该标记会被清除。远端音频只在合并刚刚删除某条转写时才会被删掉。

有两个值得知道的限制：小到可以整段上传的录音本来就没有转换副本，所以其他设备拿不到它的音频；上传会把整个文件读进内存并有 120 秒超时，所以一段八十分钟的录音（约 38 MB）需要大约 320 KB/s 的上行带宽，否则会变成一条警告，在下次同步时重试。

一台设备可以只保留文本而不保留声音：设置 › 数据 › 移除转换后的音频可以一次性释放全部空间，而那些标记会阻止下次同步把它们再拉回来。

## 强制上传与强制下载

两者都跳过合并。强制上传用本地文件覆盖远端，会丢掉上次同步之后的远端改动；强制下载则相反。两者都在与普通同步相同的锁和进行中保护之下运行，也都有确认对话框说明哪一边会被覆盖。如上所述，强制下载对转写记录只增不删：下载来的内容会写入，但本地不会被删掉任何东西。

## 自动同步

`AutoSyncService` 封装了共享调度器。触发条件是固定的：启动时一次、恢复前台时一次、每 15 分钟一次，以及最后一次本地保存之后 30 秒（尾沿去抖，所以一连串编辑只会触发一次同步）。转写完成、重命名、删除以及在阅读器里做的修改都算作保存；正在运行的任务每完成一个窗口的写入不算，否则一段录音就会带来几十次同步。重叠的触发会被进行中保护丢弃。后台发现的冲突**不会**在后台解决——状态会变成"存在待处理冲突"，等待用户打开同步页。

## API 密钥

密钥不属于模块，所以不会随模块传输。它们单独交换，而且只在端点安全时交换。交换在引擎返回之后立刻于 WebDAV 门面内进行，使用同一台服务器和同一个远端目录，用条件式 PUT 而不是引擎的锁——密钥文件是按来源"最后写入者胜出"的映射，没有基线快照也没有合并状态，所以并发写入只会变成一次被拒绝的请求和一次重新合并，而不是丢失更新。把它放进加锁的窗口里，就意味着为了一个应用去改动四个应用共用的引擎，却换不到任何安全性。

安全的判定标准以及提示给用户的内容，见 [`features/secure-secrets-sync.md`](features/secure-secrets-sync.md)。

## 凭据

WebDAV 服务器地址、用户名和密码以明文存放在 `webdav_config.json` 中，与同系列应用一致。隐私政策中对此有说明。该文件永远不会被同步、备份或导出。
